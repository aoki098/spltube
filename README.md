# splive

スプラトゥーンの配信者が「今誰が配信しているか」「直近24時間に誰が動画を上げたか」を1ページでまとめて確認できるWebアプリです。

**公開URL: https://splive-jp.com**

## 作った背景

スプラトゥーンの配信を見るとき、「誰が配信しているのか分かりづらい」という不便さがありました。
YouTubeとTwitchに配信者が分散していて、それぞれのプラットフォームを開いて確認する必要があり、
さらに「配信はしていないが新しい動画は上がっている」というケースは見逃しがちです。

追いかけたい配信者の状況を1ページで把握できるようにしたい、というのがこのアプリの出発点です。

## 主な機能

- **配信中の一覧** — YouTubeとTwitchの配信を区別せず、同時接続者数の多い順に表示
- **新着動画の一覧** — 直近24時間に投稿された動画を、再生数の伸び順に表示
- **新着ショートの一覧** — 同じく直近24時間のショート動画を再生数の伸び順に表示
- サムネイル・タイトル・同時接続者数を表示し、カードをタップするとそのまま視聴ページへ遷移
- チャンネルの登録はDjango管理画面から行う(閲覧者はログイン不要)

現在61チャンネル(YouTube 56 / Twitch 5)を登録しています。

## 技術構成

| 領域 | 使用技術 | 選定理由 |
|---|---|---|
| Webフレームワーク | Django 6.1 | 管理画面が標準で付属しており、チャンネル登録用の画面を自前で作らずに済むため |
| データベース | SQLite | データ量が数百KB、書き込みは10分に1回のバッチのみ。RDSを立てる必要がないと判断 |
| インフラ | AWS EC2 (t3.micro) + Elastic IP | 東京リージョン。長期インターンでAWSを使った経験を活かせるため |
| Webサーバー | Nginx + Gunicorn (Unixソケット) | 静的ファイル配信とアプリケーションの役割分担 |
| HTTPS | Let's Encrypt (certbot) | 自動更新を含めて無償で運用できるため |
| バックアップ | Amazon S3 | サーバーと別のサービスに置くことで、EC2が失われてもデータが残る |
| 外部API | YouTube Data API v3 / Twitch Helix API | — |
| 定期実行 | cron | 配信チェックは10分おき、新着動画チェックは1時間おき |
| 監視・通知 | Amazon SNS | 異常を検知したらメールで通知 |

`djangorestframework` を導入していますが、これは将来のネイティブアプリ版でAPIを提供するためのもので、現時点のWeb版では使用していません。

## 設計上の工夫

### YouTube APIのクォータ制約への対応

YouTube Data API v3 には1日10,000ユニットという上限があります。
当初は配信中かどうかを調べるために `search.list` を使おうとしましたが、
これは**1回あたり100ユニット**を消費します。40チャンネルを10分おきにチェックすると
1日約58万ユニットとなり、上限の58倍で全く現実的ではありませんでした。

そこで、処理を性質ごとに分けました。

**配信中の判定はスクレイピングで行う。**
チャンネルの `/live` ページを取得し、HTML内に `"isLive":true` が含まれるかで判定します。
APIを使わないためクォータを消費しません。10分おきという高頻度の処理をここに寄せています。

ただしこれだけでは、配信開始前の待機所も「配信中」と判定されてしまいます。
そこで最終確認として、すでに取得済みのAPIデータの `liveBroadcastContent` が `live` かどうかを見ています。
スクレイピングで無料で絞り込み、APIで確定させる、という役割分担です。

**新着動画の取得は公式APIで行う。**
`playlistItems.list` は**1回1ユニット**で済みます。
またチャンネルIDの `UC` を `UULF` / `UUSH` に置き換えると、
それぞれ「通常動画のみ」「ショート動画のみ」の再生リストとして扱えるため、
動画とショートを1回ずつの呼び出しで分離して取得できます。

**取得した動画の詳細はまとめて1回で取る。**
`videos.list` は動画IDをカンマ区切りで最大50件まで受け取れて、それでも消費は1ユニットです。
再生数と配信情報を1本ずつ取得していた実装を、全チャンネル分をまとめて取得する形に変更しました。
これによりクォータ消費が `2 × チャンネル数 + 3` とほぼ線形かつ予測可能になり、
**約200チャンネルまで対応できる**見込みです。

現在は61チャンネルで1日あたり約3,100ユニット(上限の31%)で運用しています。

### RSSフィードを試して取りやめた経緯

新着動画の取得には、クォータを消費しないYouTubeのRSSフィードという選択肢もありました。
実際に一度実装しましたが、同じURLが成功と404をランダムに返す状態になり、
リクエスト間隔を10秒・20秒と広げても12回連続で404が返るなど、
**レート制限が厳しく実用に耐えませんでした**。

「クォータを消費しない代わりにレート制限を受ける」というトレードオフで、
規模が大きくなるほど不利になる構造だったため、公式APIに戻す判断をしました。

### 取得に失敗したときにデータを壊さない

外部APIは失敗します。当初の実装では、取得失敗時に「新着動画なし」として
DBを上書きしてしまい、**正しく表示されていた動画が消える**という不具合が起きました。

現在は「新着なし」と「取得失敗」を別の値として区別し、
取得失敗の場合はそのフィールドを更新しないようにしています。

```python
# 動画・ショートは「取得できた時だけ」更新する
# (取得失敗(None)の時に上書きすると、前回の正しい情報が消えてしまうため)
if video is not None:
    defaults.update({...})
```

同じ考え方を配信情報にも適用しており、
「スクレイピングでは配信中と分かったが、詳細の取得に失敗した」場合は
`is_live` だけを更新し、タイトルとサムネイルは前回の値を残します。

### 壊れていることに気づけるようにする

公開してからしばらくの間、YouTubeの配信が1件も表示されない状態が続いていました。
原因はYouTube側のHTMLの変更で、判定に使っていた文字列が消えていたことです。

エラーは一切出ませんでした。ただ静かに「誰も配信していない」と判定され続けていただけです。
気づいたのはログを数えたときで、配信を検知できた回数がYouTube 0件・Twitch 47件と偏っていました。

同じ種類の不具合を3回踏んでいます。RSSが404を返しても「新着動画なし」として処理していた件、
ショート用の再生リストが404でも「取得失敗」として処理していた件、そしてこの件です。
いずれも**外部が返した想定外の反応を、正常な答えとして受け取ってしまう**という構造でした。

前項の「失敗を失敗として扱う」だけでは、この不具合は防げません。
こちらのコードは正常に動いていて、外部の仕様が変わっただけだからです。

そこで日次の健全性チェックを追加しました。24時間配信し続けているチャンネルを1つだけ見て、
配信中と判定できなければAmazon SNS経由でメールが飛びます。
常時配信のチャンネルが「配信していない」と判定されるのは判定の仕組みが壊れたときだけなので、
誤報がほとんど出ません。あわせてDBの最終更新時刻も見て、定期実行が止まっていないかを確認しています。

```bash
python manage.py check_health
```

### バックアップとIAMロール

SQLiteのファイルを日次でS3に保存しています。実装で気をつけた点が3つあります。

- **`cp` を使わない。** 書き込み中のSQLiteファイルを単純にコピーすると壊れたファイルができる可能性があるため、`sqlite3 db.sqlite3 ".backup ..."` でSQLite自身にロックを取らせています。
- **送る前に検証する。** `PRAGMA integrity_check` を通してからアップロードします。壊れたバックアップを保存してしまうと、バックアップがあるのに復元できない状態になるためです。
- **アクセスキーをサーバーに置かない。** EC2にIAMロールをアタッチし、一時的な認証情報で認証しています。権限はこのバケットへの `PutObject` / `GetObject` / `ListBucket` のみで、`DeleteObject` は与えていないため、サーバー側からバックアップを削除することはできません。

S3のライフサイクルルールで30日経過したバックアップは自動削除されます。
実際にS3からダウンロードして中身のレコードを読み出せることも確認済みです。

## ローカルでの動かし方

```bash
git clone <this repository>
cd spltube

python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

プロジェクト直下に `.env` を作成します。

```
YOUTUBE_API_KEY=<YouTube Data API v3のキー>
TWITCH_CLIENT_ID=<Twitchアプリのクライアントid>
TWITCH_CLIENT_SECRET=<Twitchアプリのクライアントシークレット>
DEBUG=True
ALLOWED_HOSTS=
```

```bash
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

`http://127.0.0.1:8000/admin/` からチャンネルを登録するか、以下のコマンドで登録できます。

```bash
python manage.py register_channel <YouTubeのハンドル名>
python manage.py register_twitch_channel <Twitchのユーザー名>
```

### ステータスの更新

```bash
python manage.py check_status               # 配信中のみチェック(10分おき用)
python manage.py check_status --mode full   # 新着動画もチェック(1時間おき用)
```

チャンネル数が増えたときにクォータを節約するため、処理を2つのモードに分けています。

### テスト

```bash
python manage.py test streams
```

モデル・一覧ページの表示と並び順・外部API呼び出し部分を対象に32件のテストがあります。
外部APIを呼ぶ箇所は `unittest.mock` でモックに差し替えているため、APIキーなしで実行できます。

`videos.list` をまとめて呼ぶ処理については、**API呼び出しが何回発生したか**を検証しています。
呼び出し回数がそのままクォータ消費量になるため、ここが崩れると上限に到達してしまうためです。
